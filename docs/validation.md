# 验证记录与限制

## 2026-10-25 的初始个案

以下是一位使用者的环境与反馈，不是多地区统计样本：

- 德国，SIM 卡插入 CPE，电脑通过网线上网，使用者表示未开代理。
- 普通投稿视频正常，多个直播间无法播放，最初显示 `92002`。
- 使用者尝试无痕窗口及播放器的主线、备线后，反馈仍无法播放。
- 从同一电脑读取公开直播播放地址接口成功，部分默认媒体服务器连接超时。
- 在该次检查中，`cn-gotcha204` 的 AVC 与 HEVC fMP4 播放列表返回 HTTP 200；各读取少量媒体样本返回 HTTP 206。
- 加入备用节点的 0.2.0 版本安装后，使用者明确反馈可以播放。0.2.1 的修复逻辑与 0.2.0 相同。

故障发生期间，不同时间的接口分配结果也有变化。这里只记录检查到的现象，不将特定服务器判定为永久故障。

## 本次复发排查与 0.3.0

同一使用者再次遇到多个直播间 `92002`，旧脚本仍显示“已加入 fMP4 备用节点”。此次检查结果：

- 播放地址接口成功，房间处于直播状态。
- 默认 `ov-gotcha207` / `ov-gotcha207b` fMP4 线路连接超时。
- 旧版固定的 `cn-gotcha204` 备用地址在此次检查中返回 HTTP 403；这与初次成功时不同。
- 使用一致的浏览器 User-Agent 请求接口和媒体时，当次返回的官方 FLV 线路返回 HTTP 200。未使用该浏览器 User-Agent 的 FLV 测试曾返回 403，不能把两种请求混为一谈。
- 已安装的 FFmpeg 读取同次官方 AVC FLV，完成约 3 秒、60 帧解码，退出成功；没有保存直播媒体文件。
- 0.3.0 改用每次响应中的官方 FLV，所选线路的编码、画质、服务器、路径和签名保持原样。它筛除其他格式，避免原播放器仍选择故障 HLS。
- 独立 Chrome 中，直接播放器页面和包含同源 iframe 的实际赛事页面都出现画面。后者持续播放超过一分钟，视频处于播放状态、解码帧数增加，所选 FLV 返回 HTTP 200。
- 同一使用者在实际使用的浏览器更换本地 0.3.0 后，明确确认恢复播放。

此次独立 Chrome 验证使用隔离的匿名环境。尚未验证所有登录状态、画质和直播间。前次 0.2.x 的自动化浏览器验证曾受验证码影响；不能将该限制套用为此次 0.3.0 的验证结果。

现象支持“当前网络下部分媒体线路不可用”的判断，不能据此确认故障发生于运营商、CPE、CDN 服务器或签名规则中的哪一环。

## 不应混为一谈的错误

最初的 `92002` 出现在没有使用此修复脚本时。未公开试验版 0.1.0 强制选择 TS 后，出现 `92006`。后者是该试验方案带来的兼容性问题，不能作为原始故障的佐证。

0.3.0 使用原播放器已实际验证可播放的官方 FLV，没有恢复 TS 试验，也没有声称所有格式均被保留。

## 自动检查能证明什么？

当前 14 项离线测试使用合成播放信息，覆盖：

1. 官方 FLV 筛选，以及所选流的编码、画质、服务器、路径、签名和其他字段完整保留。
2. 缺少合适 AVC FLV、非官方地址、非目标路径及已经只有 FLV 时不改写。
3. Fetch 字符串与 Request 对象、XHR 文本与 JSON 响应。
4. 请求参数、身份凭据选项和取消信号透传。
5. 页面预载信息、重复读取、XHR 对象复用。
6. 业务错误、HTTP 错误、非 JSON、网络异常和其他网站保持原行为。
7. 每次请求保留各自新的官方地址和签名，不缓存前一次结果。
8. 播放器 iframe 的处理和状态消息，以及直播页创建的同源空白 iframe；其他网站创建的空白 iframe 不挂钩。

这些检查验证数据处理逻辑，不能单独证明真实播放器可以连接媒体或持续播放。上述真实播放结果为另行验证。

## 尚未验证

- 其他国家、运营商、设备、全部浏览器和脚本管理器版本。
- 所有直播间、登录状态、编码、画质、直播持续时长及跨时段可用性。
- 与其他改写播放地址脚本同时启用时的行为。
- FLV 与其他格式的延迟、画质选项差异，以及全部播放器控制操作。
- 未来 B站接口、播放器、签名规则或 CDN 调度变化后的兼容性。

## 如何补充有效反馈？

使用问题模板，记录大致国家/网络类型、浏览器、脚本版本、报错、左下角状态，以及关闭脚本后的对比。多次试播和持续播放时长能帮助判断稳定性。

不要上传 Cookie、授权头、完整签名媒体地址、账号截图或未经脱敏的 HAR/网络日志。
